# time-to-event requirements matrix

> Source-backed requirement matrix for the safety.viz **time-to-event** (Kaplan–Meier Time-to-Event Explorer) module — the interactive half of the KM chart-family requirement, **Phase 1** ([safety.viz#128](https://github.com/jwildfire/safety.viz/issues/128); parent requirement [obot.roadmap#161](https://github.com/jwildfire/obot.roadmap/issues/161), design [161_design.html](https://jwildfire.github.io/obot.roadmap/requirements/design/161_design.html)). Requirement IDs use the module's condensed `TTE-*` scheme cited in the source JSDoc, the tests, and [`docs/time-to-event-coverage.md`](https://github.com/jwildfire/safety.viz/blob/main/docs/time-to-event-coverage.md). IDs are the **base** form so each row resolves the matching `requirementIds` tag in the shipped `docs/evidence/time-to-event/evidence.json`, which the evidence pages look up by exact ID. The `Evidence Type` column routes rows: `unit` → Vitest (`tests/unit/time-to-event/`, `tests/unit/demo-data/tte.test.js`), `browser` → Playwright (`tests/e2e/time-to-event.spec.js`); where a row is covered by both suites the browser evidence is listed. Treat this as a reviewed starting matrix: the rows are AI-reviewed **in an unattended session** and awaiting human sign-off — design decisions D1–D6 are adopted provisionally, and the module ships marked **Experimental** until @jwildfire's review.

## Requirement context

- Requirement: [obot.roadmap#161](https://github.com/jwildfire/obot.roadmap/issues/161) — Kaplan–Meier time-to-event chart family, interactive renderer (Phase 1)
- Implementation: [safety.viz#128](https://github.com/jwildfire/safety.viz/issues/128)
- Mandate chain: the [FDA ST&F static-displays assessment](https://jwildfire.github.io/obot.roadmap/reports/fda-stf-static-displays-plan-2026-07-21/) (figures F1/F4/F11/F13/F14 collapse onto one KM engine; mandated furniture = at-risk + cumulative-event strips, pointwise 95% CI, earliest-qualifying-event semantics) and the [goal atlas](https://jwildfire.github.io/obot.roadmap/reports/goal-atlas-2026-07-24/requirements.html) candidate C3.
- Phase 2 (out of scope here): Aalen–Johansen competing-risk display, landmark analyses, hazard-ratio / log-rank annotation, in-browser TTE derivation from raw domains, the gsm.safety widget binding.

## Scope

**Phase 1 (this matrix):** one renderer consuming an ADTTE-shaped analysis dataset (id, group, `PARAM`/`PARAMCD`, `AVAL` in days, `CNSR` with ADaM semantics): Kaplan–Meier step curves per treatment group with censoring tick marks, pointwise 95% confidence bands (Greenwood variance, log-log transform — the `survival::survfit conf.type="log-log"` interval), an in-canvas at-risk / cumulative-events strip table aligned under the time axis, an endpoint picker, orientation (cumulative incidence default) and CI toggles, configured filters, counted-and-exportable dropped rows, and event-step click dispatching the shared `participantsSelected` event.

**The organizing principle is a single derivation** (design §1): one `km.js` pass produces the curve, the band, the censor marks and every number in the strip table, so the classic KM defect — a risk table that disagrees with its own curve — is structurally impossible rather than tested away.

**Statistical honesty is a requirement, not a footnote** (design §3.4–3.5): the axis always names the estimator, the bands are labelled pointwise, the 1 − KM competing-risks overestimation is stated in-app and worked through in the clinical guide against the demo's own censored deaths, and degenerate inputs (all-censored groups, sparse endpoints, exhausted risk sets) draw honestly or say why they cannot.
